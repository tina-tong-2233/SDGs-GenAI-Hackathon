# WorkBuddy AI 接入计划

目标：让 GitHub Pages 上的 LoopMove 接收任意房间照片，通过后端调用 WorkBuddy，返回可核对的物品结果，并继续使用现有目录、尺寸和装箱逻辑。

本文件是待实施计划，不代表服务已经接通。官方资料核查日期：2026-10-01。

## 1. 先确认接入产品与图片能力

WorkBuddy 开放平台提供 OAuth 2.1、云端任务、ACP 通道和会话产物能力，见 [第三方应用文档](https://open.workbuddy.cn/docs/third-party-app) 和 [Open API 文档](https://open.workbuddy.cn/docs/openapi)。这些能力不能直接等同于一个同步的图片识别 API。

当前查看的云端任务创建接口以 `prompt` 和 `name` 为输入，未确认直接上传图片并返回物品框选 JSON 的完整方式。实施前需要确认：

- 使用个人 WorkBuddy 开放平台，还是另行评估 [WorkBuddy Enterprise](https://cloud.tencent.cn/document/api/1831/138581)；两者授权与运行方式不同。
- 应用申请、可用权限、授权回调、调用额度与计费。
- 图片附件通过哪个官方机制传入，是否支持图片视觉分析及边界框输出。
- 如何收集任务完成结果，是否需要 ACP / SSE、轮询或下载产物。

建议先验证开放平台的云端任务路线：注册应用 → OAuth 授权 → 后端创建任务 → 按官方支持的机制传入图片 → 获取最终结果。此路线是待验证方案。

**验收**：用一张非演示照片得到真实可见物品的结构化结果，确认图片确实被处理、结果不是预置数据。若无法验证图片能力，暂停该路线并确认其他可用视觉服务；只有实际调用 WorkBuddy 时才标记为 WorkBuddy 来源。

## 2. 建立独立后端

建议新增 `server/`，采用 Node.js / TypeScript，实现应用接口和供应商适配层。浏览器不直接持有 WorkBuddy 长期凭证。

```text
GitHub Pages 前端
  → LoopMove HTTPS 后端
  → WorkBuddy 授权 / 云端任务 / 图片处理
  → 最终结果解析和结构校验
  → LoopMove observations
```

建议接口（均为 LoopMove 自定义接口）：

| 接口 | 用途 |
| --- | --- |
| `GET /auth/workbuddy/start` | 发起用户授权 |
| `GET /auth/workbuddy/callback` | 校验 state，交换并保存令牌 |
| `POST /api/vision/inspect` | 接收单张图片，创建识别作业 |
| `GET /api/vision/jobs/:jobId` | 查询作业进度与最终结果 |

采用作业模型：上传返回 `202` 和 `jobId`，前端查询 `pending / running / succeeded / failed` 状态；成功时返回 `observations`。这是新的协议，需要同时修改目前只接受同步 JSON 的前端适配器。

后端任务：

- 完成 OAuth 回调、令牌安全存储与刷新；客户端密钥放在部署环境变量中。
- 校验真实文件类型、大小和照片数量，生成内部 photoId / jobId。
- 实现 WorkBuddy provider，解析其响应封装与最终产物，而非直接透传供应商 JSON。
- 校验物品数组、唯一 ID、数量、置信等级及归一化边界框；不合法结果返回明确错误。
- 对未知品类保留原始名称，不编造尺寸或强制套用物流目录。
- 限制请求频率、作业并发与使用额度；上传前告知图片将交由 AI 服务处理，处理后按明确期限清理图片。
- 配置登录与授权校验，以及 GitHub Pages origin 的 CORS。跨域 Cookie 如受浏览器限制，可评估前端短期会话令牌方案；CORS 本身不代替鉴权。

**验收**：有效图片返回可解析结果；无授权、非法图片、额度不足和上游失败都有稳定错误响应，日志不包含完整令牌。

## 3. 改造当前前端适配器

主要修改 `features/scan/index.html` 和 `features/scan/scan-logic.js`：

- 将原始 `File` 独立保存在以 photoId 为键的映射中，避免标准化和 session 克隆后丢失文件。
- 追加照片只提交新文件，不把本地 `blob:` URL 发给后端，也不重新覆盖已核对的旧结果。
- 为 `createWorkBuddyRecognizer()` 加入创建作业、轮询、超时、取消和明确的错误解析。
- 增加并发限制与有限重试，仅对可重试错误重试，避免重复创建收费作业。
- 对缺少数组或结构错误的响应报错；合法空数组才表示“没有检测到物品”。
- 使用后端返回的实际 provider 信息展示来源，区分离线演示、实时结果和失败状态。
- 配置接口时使用完整 HTTPS 地址，例如 `https://<后端域名>/api/vision/inspect`；公开配置只包含地址，不包含密钥。
- 如需要实时画面分组，扩展响应协议并接收 `groups`；第一版可先支持按物品查看。

**验收**：任意新照片能展示真实结果；追加照片可上传且保留旧编辑；失败有明确提示，不自动替换成 fixture。

## 4. 定义结果协议与多照片关联

建议完成结果使用以下结构；这是目标协议，当前前端需要调整后才能完整支持：

```json
{
  "status": "succeeded",
  "provider": "workbuddy",
  "photoId": "photo-1",
  "observations": [
    {
      "id": "obs-photo-1-desk",
      "entityId": "entity-session-1-desk",
      "displayLabel": "书桌",
      "catalogKey": "desk",
      "quantity": 1,
      "certainty": "high",
      "bbox": { "x": 0.1, "y": 0.2, "w": 0.5, "h": 0.4 }
    }
  ]
}
```

`bbox` 相对整张图片归一化，`certainty` 为 `high / medium / low`；`catalogKey` 可为空。模型识别与物流目录匹配分开，尺寸仍由品类估算或人工测量提供。

当前 `rebuildEntities()` 仅按 `entityId` 合并，多张照片各自独立识别不能自然保证 ID 一致。先跑通单张，再引入 `scanSessionId`、批量任务或服务端关联步骤，分配会话内稳定 ID。不能确定是同一物品时保留为独立实体，并提供人工合并 / 拆分操作。

**验收**：同一桌子的不同角度只计一次；两张不同桌子保持独立；不确定关联可由用户纠正。

## 5. 部署与端到端验证

- 前端：GitHub Pages，保留现有相对资源路径。
- 后端：独立 HTTPS 托管服务，配置应用凭证、回调地址、会话存储、CORS 和额度限制。
- 仓库：提交 `.env.example` 的变量名，忽略 `.env`、上传文件与令牌存储；不提交实际凭证。
- 离线演示模式继续可用，并明确标记；实时模式由部署配置启用。

必要验证：

1. 五张原图的离线匹配仍可使用。
2. 非演示照片经过真实 WorkBuddy 调用后返回结果。
3. 未知物品正常显示，未补充尺寸前不进入体积计算。
4. 空结果、非法 JSON、授权过期、限流和超时分别显示合理状态。
5. 追加照片保留文件与旧编辑，多角度去重不会误合并不同物品。
6. 在 GitHub Pages 的实际域名下完成授权、上传和结果展示，检查移动端跨域会话行为。

## 推荐实施顺序

| 阶段 | 交付物 | 进入下一阶段的条件 |
| --- | --- | --- |
| P0：能力验证 | 最小 WorkBuddy 图片识别样例、确认的官方输入与输出方式 | 非演示照片真实识别成功 |
| P1：单张链路 | 后端授权与作业接口、前端适配器 | 在线上传并显示结果 |
| P2：多张链路 | 会话关联、稳定 entityId、追加与纠正流程 | 去重和编辑保留通过验证 |
| P3：发布 | Pages 配置、独立后端、错误与额度控制 | 实际线上域名完成端到端验证 |

第一步需要准备：WorkBuddy 应用类型、已开通权限、官方图片输入说明，以及可用于开发环境的授权配置。凭证通过本地环境变量或部署控制台提供。
